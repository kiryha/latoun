# Latoun Local Configurator v0.1 — Coding Brief

## 1. Objective

Build the first local web configurator for Latoun.

This is an internal prototype, not a customer-facing website. Its primary purpose is to test the Latoun product model, database structure, geometry-loading workflow, material system, and configuration-resolution logic.

The application must allow the user to configure a single 1-gang Latoun wall assembly by selecting:

- Device type:
  - Switch
  - Rotary dimmer
- Physical material:
  - Brass
  - Steel

The application must load the corresponding GLB assets, apply the selected Three.js material, display the assembled product, generate a simple BOM, and allow the configuration to be saved locally.

Read the repository `README.md` before implementation. It contains the broader Latoun product model and long-term architecture.

# 2. Current Geometry Assets

The following GLB files already exist:

```text
1gang_plate.glb
1gang_plate_screws.glb
1gang_slot01_dimmer.glb
1gang_slot01_switch.glb
```

The configurator assembly consists of:

```text
1-gang assembly
=
1gang_plate.glb
+ 1gang_plate_screws.glb
+ selected slot module:
    1gang_slot01_dimmer.glb
    or
    1gang_slot01_switch.glb
```

All assets are exported from Houdini in final assembly coordinates.

Requirements:

```text
position = 0, 0, 0
rotation = 0, 0, 0
scale = 1, 1, 1
```

Do not add runtime positioning logic for individual parts.

All loaded assets must be added at the scene origin.

# 3. MVP User Flow

The application should open on one configurator page.

The user must be able to:

1. Select `Switch` or `Rotary Dimmer`.
2. Select `Brass` or `Steel`.
3. See the 3D assembly update immediately.
4. Rotate and zoom the product.
5. See the resolved configuration data.
6. See a basic generated BOM.
7. Save the configuration to the local SQLite database.
8. Reload previously saved configurations.
9. Export the active configuration as JSON.

The default configuration should be:

```text
Device: Rotary Dimmer
Material: Brass
```

```text

    asset_manifest.json
```

# 7. Asset Manifest

Create:

```text
config/asset_manifest.json
```

The asset manifest is the registry that connects stable semantic asset keys to physical GLB paths.

Use the current short filenames. Do not require full `latoun_us_mcm_*` filenames yet.

Example:

```json
{
  "schema_version": 1,
  "assets": {
    "plate.1gang": {
      "asset_type": "plate",
      "file": "/assets/glb/1gang_plate.glb",
      "coordinate_space": "assembly_origin",
      "material_policy": "replace_all"
    },
    "hardware.1gang.plate_screws": {
      "asset_type": "hardware",
      "file": "/assets/glb/1gang_plate_screws.glb",
      "coordinate_space": "assembly_origin",
      "material_policy": "replace_all"
    },
    "module.1gang.slot01.dimmer": {
      "asset_type": "slot_module",
      "module_type": "dimmer",
      "slot_position": 1,
      "file": "/assets/glb/1gang_slot01_dimmer.glb",
      "coordinate_space": "assembly_origin",
      "material_policy": "replace_all"
    },
    "module.1gang.slot01.switch": {
      "asset_type": "slot_module",
      "module_type": "switch",
      "slot_position": 1,
      "file": "/assets/glb/1gang_slot01_switch.glb",
      "coordinate_space": "assembly_origin",
      "material_policy": "replace_all"
    }
  }
}
```

For v0.1, `material_policy: "replace_all"` means that the frontend replaces every material found inside that GLB with the selected brass or steel material.

This is temporary but intentional. It avoids requiring semantic material bindings before the geometry pipeline is finalized.

Later, `replace_all` can be replaced with named bindings such as:

```text
bind_plate_body
bind_visible_screws
bind_actuator_primary
bind_core_visible
```

Do not build that more advanced system yet.

Use SQLite.

The first database should contain only the entities needed by this iteration.




# 13. Three.js Rendering Requirements

Use:

```text
React Three Fiber
OrbitControls
PerspectiveCamera
GLTFLoader through useGLTF
```

Scene requirements:

```text
neutral background
environment lighting
one or two soft lights
contact shadow or soft ground shadow
orbit controls
zoom enabled
pan disabled
reasonable camera framing
```

All assets must load at the origin:

```typescript
loadedAsset.position.set(0, 0, 0);
loadedAsset.rotation.set(0, 0, 0);
loadedAsset.scale.set(1, 1, 1);
```

Do not create per-asset position tables.

When `material_policy` is `replace_all`:

1. Traverse the loaded GLB scene.
2. Find every `THREE.Mesh`.
3. Replace all existing materials with the selected resolved material.
4. Preserve the geometry and transforms.
5. Clone materials only when necessary.

Dispose replaced materials and textures correctly when configurations change to avoid memory leaks.

The asset loader should produce a clear error if a GLB cannot be found.

# 14. Configuration Changes

When the material changes:

```text
Do not reload geometry if avoidable.
Update the Three.js material assignment.
Update the configuration summary.
Update the prototype BOM.
```

When the device type changes:

```text
Keep the plate loaded.
Keep the screws loaded.
Remove the previous slot module.
Load the selected slot module.
Apply the active material.
Update the prototype BOM.
```

The selected configuration should resolve automatically. A separate Validate button is not required for this limited MVP.

# 15. Saving and Exporting

## Save

When the user selects `Save Configuration`:

1. Send the semantic configuration to the backend.
2. Generate a configuration code such as `LAT-CFG-000001`.
3. Save it in SQLite.
4. Refresh the saved configuration list.
5. Show a visible success message.

## Export JSON

Export a JSON file containing:

```json
{
  "configuration_code": "LAT-CFG-000001",
  "gang_count": 1,
  "module_type": "dimmer",
  "material": "brass",
  "assets": [
    "plate.1gang",
    "hardware.1gang.plate_screws",
    "module.1gang.slot01.dimmer"
  ],
  "prototype_bom": []
}
```

The exported filename should be:

```text
LAT-CFG-000001.json
```

For unsaved configurations:

```text
latoun_configuration_draft.json
```

# 17. Local Setup and Run Scripts

Create two Windows batch files in the repository root.

## `setup_local.bat`

The script should:

1. Verify that Python is available.
2. Verify that Node.js and npm are available.
3. Create a Python virtual environment at `.venv` if it does not exist.
4. Install backend Python dependencies.
5. Run `npm install` inside `frontend`.
6. Initialize and seed the SQLite database.
7. Print clear completion instructions.

Do not reinstall everything unnecessarily on every run.

## `run_local.bat`

The script should:

1. Activate `.venv`.
2. Start FastAPI on port `8000`.
3. Start the Vite frontend on port `5173`.
4. Open the default browser at:

```text
http://localhost:5173
```

5. Keep the backend and frontend terminal windows visible so errors can be inspected.

# 22. Acceptance Criteria

The iteration is complete when:

1. `setup_local.bat` prepares the project on a Windows PC.
2. `run_local.bat` launches the backend and frontend.
3. The browser opens the local configurator.
4. The plate and screws are always visible.
5. The user can switch between dimmer and switch geometry.
6. The user can switch between brass and steel.
7. All geometry loads at the origin without runtime positioning.
8. Material parameters come from SQLite.
9. GLB paths come from `asset_manifest.json`.
10. The backend returns a resolved render state.
11. A prototype BOM is displayed.
12. Configurations can be saved and reloaded.
13. The active configuration can be exported as JSON.
14. No GLB paths or material parameters are hardcoded in React components.

The purpose of this iteration is not visual perfection. It is to prove that the Latoun configuration, asset, material, database, and rendering layers work together cleanly.
